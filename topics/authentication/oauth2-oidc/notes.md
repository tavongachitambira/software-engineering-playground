# OAuth 2.0 and OpenID Connect 


### WHAT PROBLEM THIS SOLVES
When applications need to access a user's data from third-party services, asking the user for their raw login credentials (username and password) is a massive security hazard that forces developers to store plain text passwords, grants third parties overly broad access without expiration, and makes individual access revocation impossible without changing the master password. OAuth 2.0 solves this delegation problem by introducing a secure authorization layer that separates the client from the resource owner, issuing limited, short-lived tokens instead of permanent passwords. However, raw OAuth 2.0 was designed strictly to authorize API access and is completely incapable of verifying who a user is. OpenID Connect (OIDC) solves this identity problem by overlaying a thin, standardized authentication framework on top of OAuth 2.0, enabling applications to securely verify a user's identity and active session through a single, cryptographically signed token called an ID Token.

### THE CORE MECHANISM

#### 1. The Authentication and Authorization Request (Front-Channel Redirect)
The client application (Relying Party) redirects the end-user's browser to the Authorization Endpoint of the identity provider (OpenID Provider).

* **Endpoint:** Authorization Endpoint (using TLS/HTTPS)
* **HTTP Method:** GET (serialized as query string) or POST (serialized as form data)
* **Parameters:**
  * `response_type`: MUST be `code`.
  * `client_id`: The client’s pre-registered identifier.
  * `redirect_uri`: The exact pre-registered callback endpoint.
  * `scope`: MUST contain `openid` to trigger OIDC (typically requested with `profile` or `email`).
  * `state`: REQUIRED for security. A unique, high-entropy random string generated by the client and bound to the user's browser session cookie to prevent Cross-Site Request Forgery (CSRF).
  * `nonce`: REQUIRED for OIDC. A cryptographically random, high-entropy string used to bind the browser session with the cryptographically signed ID Token to prevent replay attacks.

* **Request Shape:**
  ```
  GET /authorize?response_type=code&scope=openid%20profile%20email&client_id=s6BhdRkqt3&state=af0ifjsldkj&nonce=n-0S6_WzA2Mj&redirect_uri=https%3A%2F%2Fclient.example.org%2Fcb HTTP/1.1
  Host: server.example.com
  ```

#### 2. The Authorization Response (Front-Channel Redirect)
After user authentication and consent, the server redirects the browser back to the pre-registered redirect URI.

* **Parameters:**
  * `code`: A short-lived, single-use authorization code.
  * `state`: The exact state string sent in the request.

* **Response Shape:**
  ```
  HTTP/1.1 302 Found
  Location: https://client.example.org/cb?code=SplxlOBeZQQYbYS6WxSbIA&state=af0ifjsldkj
  ```

#### 3. Exchanging Code for Tokens (Back-Channel Post-Request)
The client intercepts the callback, verifies that the returned `state` matches its local session cookie state, and issues a secure, direct server-to-server call to exchange the code.

* **Endpoint:** Token Endpoint (using TLS/HTTPS)
* **HTTP Method:** POST
* **Content-Type:** `application/x-www-form-urlencoded`
* **Authentication:** Confidential clients MUST authenticate via their registered credentials (e.g., HTTP Basic).
  * Header: `Authorization: Basic <base64(client_id:client_secret)>`
* **Parameters:**
  * `grant_type`: MUST be `authorization_code`.
  * `code`: The authorization code received in step 2.
  * `redirect_uri`: MUST exactly match the `redirect_uri` sent in the initial request.

* **Request Shape:**
  ```
  POST /token HTTP/1.1
  Host: server.example.com
  Content-Type: application/x-www-form-urlencoded
  Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW

  grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA&redirect_uri=https%3A%2F%2Fclient.example.org%2Fcb
  ```

#### 4. The Token Response (Back-Channel Response)
The server validates client credentials, verifies the authorization code was issued to this client, matches the redirect URI, and responds.

* **Format:** `application/json` with `Cache-Control: no-store`
* **Response Shape:**
  ```json
  {
    "access_token": "SlAV32hkKG",
    "token_type": "Bearer",
    "refresh_token": "8xLOxBtZp8",
    "expires_in": 3600,
    "id_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6IjFlOWdkazcifQ..."
  }
  ```

#### 5. Relying Party Validation Sequence
Upon receipt of the token response, the client MUST validate the tokens locally:

1. **Verify Signature:** Verify the JWS signature on the `id_token` using the public key from the provider's JWKS endpoint.
2. **Verify Issuer (`iss`):** Ensure `iss` matches the provider's discovered Issuer URL exactly.
3. **Verify Audience (`aud`):** Ensure `aud` contains the client's registered `client_id`.
4. **Verify Time Claims:** Ensure the current time is before the `exp` claim.
5. **Verify Nonce:** Extract the `nonce` claim from the ID Token and confirm it matches the raw string generated in step 1 (typically stored locally as a hashed value to prevent browser exposure).

### SECURITY CONSIDERATIONS

* **Cross-Site Request Forgery (CSRF) Mitigation:** The client MUST generate and validate the `state` parameter. CSRF on the redirect callback allows an attacker to inject their own authorization code into a victim's session, binding the victim's local client application state to the attacker’s account. Ensure the `state` is a secure, unguessable value tied directly to an `HttpOnly` session cookie on the browser.

* **Replay Attack Mitigation:** The `nonce` is critical to prevent an attacker from capturing an ID Token and resending it to logging endpoints to masquerade as the user. Store the cryptographically random `nonce` in your session context, hash it, and verify that the `nonce` claim in the returned ID Token matches the hash of the cookie.

* **Browser Isolation (Front vs. Back-Channel split):** The authorization code exchange MUST occur strictly server-to-server (back-channel) over a TLS-secured channel using client authentication. This ensures access and ID tokens are never exposed to malware running inside the user-agent or browser history.

* **The HTTP 307 Redirect Security Trap:** Never redirect users using HTTP 307 during OAuth/OIDC redirects. HTTP 307 preserves the original HTTP POST request format and body data, which will silently leak user credentials (such as passwords entered at the login screen) to the client's redirect URI. Enforce HTTP 303 or 302 redirects instead.

### COMMON MISCONCEPTIONS

* **OAuth 2.0 is an Authentication Protocol:** OAuth 2.0 is strictly an authorization delegation framework. It is designed to issue access tokens, which are completely opaque to the client application and carry no standard, structured format to verify who authenticated. Attempting to use OAuth 2.0 alone for identity management creates severe user-impersonation and token-injection vulnerabilities. Authentication requires OpenID Connect (OIDC).

* **`state` and `nonce` parameters are interchangeable:** They protect completely different trust boundaries. `state` is a front-channel browser-session validator verified by the client to mitigate CSRF. `nonce` is a cryptographic claim embedded directly inside the signed ID Token and verified by the client to prevent replay attacks.

* **The UserInfo Endpoint `sub` claim can be trusted standalone:** A client must never trust user profile claims returned from the UserInfo endpoint without validating that the returned `sub` claim exactly matches the validated `sub` claim inside the cryptographically signed ID Token. Without this check, a token substitution attack can allow an attacker to hijack a user profile session.
